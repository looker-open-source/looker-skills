# Backend Integration Choice: Direct API vs. ADK

There are two ways to wire the backend to the Conversational Analytics API. Decide during requirements gathering (§0) — it changes the backend implementation, the deployment tooling, and the frontend's streaming contract, so don't scaffold before this is confirmed.

## Direct API (what the rest of this skill assumes)

Call `DataChatServiceClient`/`DataAgentServiceClient` yourself from a FastAPI (or similar) backend, as covered in `data-agent-context.md`, `backend-deployment.md`, and `templates/backend_sse_relay.py`. Two variants per Google's own docs:

- **Single-agent**: your app calls the API directly for a straightforward text-to-answer flow. Granular control, no framework dependency — but you build auth, state management, response parsing, and error handling yourself. This is what `templates/backend_sse_relay.py` implements.
- **Custom orchestrator**: a root agent you write uses function calling to route between the Conversational Analytics API and other tools. Maximum orchestration control, but you manage the tool definitions, conversation loop, and multi-turn state by hand.

Choose this path for a single-purpose analytics chat app, when you need maximum control or portability outside the ADK ecosystem, or when you don't want an extra framework dependency.

## Agent Development Kit (ADK)

Google's [Agent Development Kit](https://google.github.io/adk-docs/) provides framework-driven orchestration (multi-agent routing, tool execution, state management) instead of you building it. Three approaches, in increasing order of relevance to this skill:

- **Schema-driven** (`BigQueryToolset`): table references only, no data agent. Fastest to prototype, but no semantic governance (no golden queries/business glossary) and stateless.
- **Governed** (`DataAgentToolset`): wraps a **pre-existing, persistent `DataAgent`** — the same resource this skill already has you create via `DataAgentServiceClient` (see `data-agent-context.md`, `templates/create_data_agent.py`-equivalent). Gives semantic governance and consistent behavior across consumers. **This is the natural ADK path if you're already following this skill's persistent-agent guidance.**
- **Custom sub-agents**: stream data asynchronously as part of a larger multi-agent graph; accesses all response types (charts, tables, SQL) for real-time feedback within a bigger agent system.

Choose ADK when the conversational analytics agent is one part of a larger multi-agent system, or you want the framework handling orchestration/state rather than hand-rolling it.

### Prerequisites

- ADK Python **v1.23.0+**.
- A **DataAgent already created** (same one-off step as the direct-API path — see `data-agent-context.md`).
- Application Default Credentials (or equivalent) with access to the project.

### Wiring a DataAgent into an ADK agent (`DataAgentToolset`)

```python
import google.auth
from google.adk.agents import Agent
from google.adk.tools.data_agent.config import DataAgentToolConfig
from google.adk.tools.data_agent.credentials import DataAgentCredentialsConfig
from google.adk.tools.data_agent.data_agent_toolset import DataAgentToolset

application_default_credentials, _ = google.auth.default()
credentials_config = DataAgentCredentialsConfig(credentials=application_default_credentials)
tool_config = DataAgentToolConfig(max_query_result_rows=100)

da_toolset = DataAgentToolset(
    credentials_config=credentials_config,
    data_agent_tool_config=tool_config,
    # list_accessible_data_agents / get_data_agent_info are optional discovery
    # tools; ask_data_agent is the one that actually chats with a DataAgent.
    tool_filter=["list_accessible_data_agents", "get_data_agent_info", "ask_data_agent"],
)

agent = Agent(
    name="data_agent_example",
    model="gemini-2.5-flash",
    tools=[da_toolset],
)
```

### Deployment differs from the direct-API path

Don't reuse `templates/Dockerfile` + `templates/backend_sse_relay.py` here — ADK has its own CLI and FastAPI scaffolding:

- **Local run**: `adk run` (terminal), `adk web` (dev UI), or `adk api_server` (FastAPI server) to validate before deploying.
- **Deploy**: `adk deploy cloud_run --project=$GOOGLE_CLOUD_PROJECT --region=$GOOGLE_CLOUD_LOCATION --service_name=$SERVICE_NAME $AGENT_PATH` — builds and deploys in one step (it will prompt "Allow unauthenticated invocations?"; answer per the same public-vs-IAP/Firebase decision made in §0).
- **The FastAPI app itself** is generated by ADK's `get_fast_api_app(agents_dir=..., allow_origins=..., web=...)` rather than one you hand-write — it exposes `/run_sse` (agent execution over Server-Sent Events, `"streaming": true/false`), plus session-management endpoints under `/apps/{app_name}/users/{user_id}/sessions/{session_id}`.

### Frontend implications

The frontend still consumes an SSE stream, but **`/run_sse`'s event shape is ADK's own, not the raw `geminidataanalytics.Message` JSON** that `templates/frontend_chat.jsx` / `frontend_data_table.jsx` parse (`systemMessage.text` / `systemMessage.data.result`). Don't assume the same parsing code applies — inspect a live `/run_sse` response and adapt before reusing those templates' rendering logic.

### State management

ADK's session service manages conversation state independently of the Conversational Analytics API's own `Conversation` resource (see "Conversation state" in `data-agent-context.md`). If you're on the ADK path, use ADK's session management for multi-turn history — don't also try to layer the direct API's `conversation_reference` on top; that guidance is for the direct-API path only.
