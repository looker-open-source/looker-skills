# Query Outliers Diagnostic & Multi-Vector Forensic Playbook

This reference document defines the **5-Vector Root Cause Forensic Framework**, 3-Way Outlier Decomposition, per-phase maximum outlier isolation methodology, query inspection recipes, and standardized reporting scorecards for diagnosing and presenting anomalous query runtimes.

---

## 🔍 Part 1: Beyond "Missing Filters" — The 5-Vector Forensic Framework

When diagnosing slow queries (even ones running with no filters), **never assume adding a filter is the only or appropriate solution**. Many business questions legitimately require full historical analysis (e.g. lifetime order count per user, customer lifetime value, all-time product performance).

Always evaluate the query against all **5 Root Cause Vectors**:

```
                          SLOW QUERY OUTLIER DETECTED
                                      │
       ┌──────────────┬───────────────┼───────────────┬──────────────┐

  phase breakdown symmetric agg)  rollups)        starvation)    at same minute)
```

### Vector 1: Multi-Phase Lifecycle Latency Decomposition
Determine where the latency was actually spent before assuming database slowness:
* Query `query_metrics` for the exact `query.id`:
  - `execute_main_query`: Physical database query execution time.
  - `acquire_connection`: Time spent waiting for an available database connection pool slot. If high (>0.24s), slowness is caused by **connection pool exhaustion**, not query complexity.
  - `queued`: Looker worker queue delay. If high (>0.1s), Looker thread pool is saturated.
  - `stream_to_cache` / `load_main_query_in_memory`: Time streaming large result sets across the network. If high, row limit or serialization is the bottleneck.
  - `postprocessing`: Client-side JavaScript/JVM calculations and formatting.

#### Telemetry Query for Query Phase Breakdown:
```json
{
  "model": "system__activity",
  "view": "query_metrics",
  "fields": [
    "query.id",
    "query_metrics.async_processing",
    "query_metrics.execute_main_query",
    "query_metrics.acquire_connection",
    "query_metrics.queued",
    "query_metrics.stream_to_cache",
    "query_metrics.postprocessing",
    "query_metrics.model_init_computed"
  ],
  "filters": {
    "query.id": "<TARGET_QUERY_ID>"
  },
  "limit": "1"
}
```

### Vector 2: SQL & Join Anti-Pattern Forensics
Inspect the physical SQL generated by Looker via `get_query_sql(query_id)`:
1. **Redundant Joined Tables**:
   * Check if Looker is `LEFT JOIN`ing tables that have no fields selected in the `SELECT` clause (e.g. joining `users` when only `orders.user_id` and `orders.count` are requested). If so, audit the Explore definition for unnecessary join dependencies or missing join conditions.
2. **Symmetric Aggregations (`SUM_DISTINCT`)**:
   * If a measure appears as `SUM(DISTINCT CAST( ... AS NUMERIC) + ... )`, Looker detected a fan-out risk due to a missing `primary_key: yes` or incorrect `relationship: many_to_one`. This creates severe computational overhead on the database.
3. **Non-Key Joins & Unindexed Predicates**:
   * Inspect whether join `ON` clauses join on unindexed strings instead of integer surrogate keys or partitioned date keys.

---

### Vector 3: Legitimate Unfiltered Workloads vs Aggregate Table Acceleration
* **Recognize Valid Full-Dataset Metrics**: When a query measures lifetime user behavior, all-time totals, or annual cohorts, **do NOT prescribe adding date filters** (which alters the business result).
* **The LookML Solution**: Prescribe **Aggregate Awareness (`aggregate_table:`)** or an **Incremental Persistent Derived Table (PDT)**.
  - An `aggregate_table` will pre-calculate and store the user order counts during off-peak hours, allowing the query to scan a pre-aggregated table of 100k rows instead of 50 million raw transaction rows.

---

### Vector 4: Warehouse Concurrency & Slot Contention
* When physical database execution is slow (`execute_main_query > 20s`), check if the warehouse was under severe resource constraints at that moment:
  - In BigQuery, query `INFORMATION_SCHEMA.JOBS_TIMELINE_BY_PROJECT` for the exact hour to check if available slots were 100% saturated.
  - In Snowflake/PostgreSQL, check if warehouse compute was undersized or queued behind heavy ETL jobs.

---

### Vector 5: Colocated Concurrent Query Bursts
* Check what other queries were running at the exact same timestamp (`history.created_time`):
  - Did a large dashboard fire 25 tiles simultaneously, consuming all 15 user connection slots?
  - Did a scheduled cron job blast fire at the top of the hour (`:00`) alongside 40 other jobs?

#### Telemetry Query for Colocated Queries:
```json
{
  "model": "system__activity",
  "view": "history",
  "fields": [
    "query.id",
    "query.view",
    "dashboard.title",
    "user.name",
    "history.created_time",
    "history.average_runtime",
    "history.status"
  ],
  "filters": {
    "history.created_date": "7 days",
    "history.created_time": "<TARGET_TIMESTAMP_WINDOW>"
  },
  "sorts": ["history.created_time desc"],
  "limit": "20"
}
```

## 🔍 Part 2: Per-Phase Maximum Outlier Isolation

To pinpoint the exact architectural failure point on an instance, query the single worst outlier across every query lifecycle phase:

| Phase | Target Outlier Field | High-Value Diagnostic Interpretation |
| :--- | :--- | :--- |
| **Async Total** | `query_metrics.async_processing` | Absolute worst user-facing query experience. |
| **Queue Time** | `query_metrics.queued` | Looker worker pool exhausted; thread contention. |
| **Connection Pool** | `query_metrics.acquire_connection` | Database connection pool limits reached or slow auth handshake. |
| **Connection Hold** | `query_metrics.connection_held` | Database connection held open too long by streaming/waiting. |
| **Per-User Throttle**| `query_metrics.per_user_throttler` | Single user exceeded 15 concurrent query cap (large dashboard / merged queries). |
| **Project Init** | `query_metrics.project_init` | Monolithic project with too many view/model files. |
| **Model Init (Comp)**| `query_metrics.model_init_computed` | Heavy un-cached model compilation; needs model scoping. |
| **Model Init (Cache)**|`query_metrics.model_init_cache` | Cache validation lag; high deployment frequency at peak hours. |
| **Explore Init (Comp)**|`query_metrics.explore_init` | Complex explore with excessive joins and dimensions. |
| **Explore Init (Cache)**|`query_metrics.marshalled_cache_load`| Heavy serialized explore schema. |
| **Prepare Time** | `query_metrics.prepare` | LookML SQL compilation lag; move calculations to DB/LookML. |
| **Database Execution**| `query_metrics.execute_main_query` | Unoptimized SQL query scanning massive raw warehouse partitions. |
| **Totals Execution**| `query_metrics.execute_totals_query` | Subtotal query executed separately from main query. |
| **Row Totals Exec** | `query_metrics.execute_row_totals_query`| Row total query executed separately from main query. |
| **Grand Totals Exec**| `query_metrics.execute_grand_totals_query`| Grand total query executed separately from main query. |
| **PDT Build** | `query_metrics.pdt` | Slow derived table materialization blocking query. |
| **Post-Processing** | `query_metrics.post_processing` | Client-side calculations, sorting, and formatting overhead. |
| **Stream to Cache** | `query_metrics.stream_to_cache` | High row counts being streamed across network to browser cache. |
| **In-Memory Loading**| `query_metrics.load_main_query_in_memory`| Non-streamed query loading massive result set into Looker RAM. |

#### Presentation Rules for Agents:
1. **Always State the Dominant Vector**: Clearly classify whether the bottleneck is Database Execution, Unnecessary Joins, Missing Aggregate Tables, Connection Contention, or Overhead.
2. **Respect Business Semantics**: Differentiate intentional full-historical scans from accidental unbounded scans.
3. **Prescribe Architecture Solutions**: Recommend LookML `aggregate_table:`, PDTs, join optimizations, or connection pooling alongside filter recommendations.
